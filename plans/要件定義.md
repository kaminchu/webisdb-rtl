# Webブラウザ版ワンセグ受信アプリ 要件定義書

## 1. 目的

本プロジェクトは、Android端末またはPC/MacにUSB接続したRTL-SDRを使用し、Webブラウザ上で日本国内の地上デジタルテレビ放送のワンセグを受信・復調・再生できるWebアプリケーションを実現することを目的とする。

USBデバイスとの通信にはWebUSBを使用し、RTL-SDRから取得したRaw IQデータをブラウザ内で処理する。

復調、MPEG-TS解析、映像・音声デコード、字幕、EPG表示などを原則としてクライアントサイドで完結させ、専用ネイティブアプリやバックエンドサーバーを必要としない構成とする。

GitHub Pagesで公開可能な静的Webアプリケーションとし、PWAとしてオフライン環境でも起動・受信可能な構成を目指す。

---

# 2. 対象環境

## 2.1 対応ブラウザ

正式対応対象は以下とする。

* Android版 Google Chrome
* Windows版 Google Chrome
* macOS版 Google Chrome

Firefox、Safari、およびその他のブラウザについては初期バージョンでは正式対応対象外とする。

Chromiumベースであっても、Chrome以外のブラウザについては動作保証を行わない。

---

## 2.2 対応端末

以下の端末環境を想定する。

* Androidスマートフォン
* Androidタブレット
* Windows PC
* Mac

Android端末についてはUSB OTGまたはUSBホスト機能を利用してRTL-SDRを接続する。

---

# 3. 対応SDRデバイス

初期対応デバイスは以下とする。

* RTL-SDR Blog V3
* RTL-SDR Blog V4

その他のRTL2832UベースのSDRデバイスについては初期バージョンでは動作保証対象外とする。

ただし、将来的に他のRTL-SDR互換デバイスを追加可能な構造とする。

RTL-SDRからはRaw IQデータを取得し、それ以降の処理は原則としてブラウザ側のソフトウェアで実行する。

---

# 4. RTL-SDR WebUSBドライバ

RTL-SDR Blog V3/V4を制御するWebUSBドライバは本プロジェクト内で独自実装する。

OSネイティブドライバやlibrtlsdrを直接利用するのではなく、TypeScriptからWebUSB APIを使用してRTL2832Uおよびチューナーを制御する。

想定される責務は以下とする。

* WebUSBデバイスの列挙
* ユーザーによるUSBデバイス選択
* USBデバイスのopen
* Configuration選択
* Interface claim
* RTL2832U初期化
* チューナー初期化
* RTL-SDR Blog V3/V4の識別
* 周波数設定
* サンプルレート設定
* Gain設定
* AGC設定
* PPM補正
* IQデータの連続取得
* USB transfer管理
* USB transfer異常の検出
* stop
* reset
* close

デバイス依存部分と上位のIQ Source APIは分離する。

将来的に他のRTL-SDR互換デバイスを追加する場合に、ISDB-T復調部分を変更する必要がない構造とする。

# 11. IQ入力抽象化

ハードウェア入力とテスト用ファイル入力を同じインターフェースから扱える構造とする。

概念的には以下のようなインターフェースを持つ。

```ts
interface IQSource {
  open(): Promise<void>;
  close(): Promise<void>;

  setFrequency(hz: number): Promise<void>;
  setSampleRate(hz: number): Promise<void>;

  start(): Promise<void>;
  stop(): Promise<void>;
}
```

少なくとも以下の実装を用意する。

```text
RTLSDRSource
IQFileSource
```

これにより、実機が存在しない環境でもDSP処理の開発・テストを可能とする。

* USB転送量
* Android端末の処理性能
* ワンセグ抽出方式
* DSP計算量
* 周波数補正
* OFDM同期精度

サンプルレートは技術設計事項として扱う。

# 13. DSP処理

基本となる処理パイプラインは以下とする。

```text
IQ取得
↓
DC除去
↓
周波数補正
↓
OFDM同期
↓
FFT
↓
キャリア復調
↓
TMCC解析
↓
デインターリーブ
↓
Viterbi
↓
Reed-Solomon
↓
MPEG-TS生成
```

必要に応じて、上記の間に追加の信号処理を挿入できる構造とする。

---

# 14. DSP実装言語

初期実装はTypeScript / JavaScriptを優先する。

最初からDSP全体をWebAssembly化しない。

TypeScript実装で性能測定を行い、リアルタイム処理に追いつかない部分を特定した上で、必要な部分のみWebAssemblyへ移行する。

想定されるWebAssembly化候補には以下がある。

* FFT
* OFDM処理
* デインターリーブ
* Viterbi
* Reed-Solomon
* その他CPU負荷の高い処理

JavaScript実装とWebAssembly実装を差し替え可能な内部設計とする。

---

# 15. Worker設計

CPU負荷の高い処理によってUIスレッドがブロックされないよう、Web Workerを積極的に利用する。

初期構成として以下を想定する。

```text
Main Thread
├─ React
├─ UI
├─ IndexedDB
├─ Video
└─ Audio

Receiver Worker
├─ WebUSB
├─ RTL-SDR制御
├─ IQ取得
├─ IQ Buffer
└─ DSP

TS Worker
├─ MPEG-TS解析
├─ PSI/SI解析
├─ EPG解析
└─ 各種メタデータ処理
```

性能上必要になった場合は、DSP処理をさらに複数Workerに分割する。

Worker間で大量データ転送を行う場合は、必要に応じて以下の利用を検討する。

* Transferable
* SharedArrayBuffer
* Ring Buffer

以下の選局方式を提供する。

## 16.3 地域からの選択

概念的には以下の対応関係を持つ。

```text

↓
送信所
↓
物理チャンネル
↓
周波数
↓

```

ユーザーが地域を選択すると、その地域で利用可能なチャンネル一覧を表示できる。

# 18. GPSによる地域選択

Geolocation APIが利用可能な環境では、現在地を利用して受信地域を自動選択できる機能を提供する。

ただし、アプリケーション起動時に位置情報権限を要求してはならない。

ユーザーが明示的に、

```text
現在地から地域を選択
```

などの機能を実行した時点で初めて位置情報権限を要求する。

GPS機能は任意機能とする。

位置情報アクセスを拒否した場合でも、手動による地域選択やチャンネル選択は利用可能とする。

# 19. チャンネル自動スキャン

物理チャンネルを順次受信し、受信可能な地上デジタル放送を検出する自動スキャン機能を提供する。

検出結果には可能な範囲で以下を含める。

* 物理チャンネル
* 周波数
* 受信可否
* Signal level
* C/N
* MER相当
* 放送局名
* Service ID
* Transport Stream ID

# 20. EPGスキャン

通常のチャンネルスキャンとは別に、EPG情報収集を目的としたスキャン機能を提供する。

受信可能な各チャンネルを順番に選局し、EIT等から番組情報を取得する。

取得したEPG情報はIndexedDBへ保存する。

---

# 21. EPG

EPG情報を複数局横断で表示できる番組表UIを提供する。

現在受信中でない局についても、過去に取得したEPG情報がIndexedDBに存在する場合は表示可能とする。

番組表から放送局またはサービスを選択すると、その局へ選局できる。

EPG情報については適切な有効期限を持たせ、古い番組情報を削除または更新できる構造とする。

# 32. バッファ破棄

ユーザーが明示的に蓄積済みバッファを破棄できる機能を提供する。

UI上では例えば以下のようなボタンを提供する。

```text
LIVEに戻る
```

または

```text
バッファを破棄
```

ユーザーがCM中などに遅延を解消する目的で利用することを想定する。

バッファ破棄操作では、単純なデータ削除だけではなく、必要に応じて以下を行う。

```text
IQ Buffer clear
↓
DSP state reset
↓
OFDM再同期
↓
TS再同期
↓
Decoder再同期
↓
最新受信位置から再生再開
```

要件としては、

「蓄積された未処理データをユーザー操作で破棄し、可能な限り最新の受信位置から復調・再生を再開できること」

とする。

# 38. 非機能要件

以下を非機能要件とする。

## 38.1 長時間安定動作

受信可能な信号環境下では、長時間継続して映像・音声を再生できること。

## 38.2 UI応答性

DSP処理によってUI操作が著しく阻害されないこと。

CPU負荷の高い処理は可能な限りWeb Workerへ分離する。

## 38.3 リアルタイム処理性能

IQサンプルの処理が継続的にリアルタイム入力速度を下回らないこと。

長時間平均で、

```text
DSP処理速度 >= IQ入力速度
```

となることを目標とする。

## 38.4 バッファ可視化

処理遅延および内部バッファ蓄積量をユーザーが視覚的に確認できること。

## 38.5 バッファ破棄

ユーザー操作によって蓄積済みバッファを破棄し、最新の受信位置への復帰を試みられること。

---

# 39. エラー処理

USB抜去、OTG切断、画面スリープ、バックグラウンド移行、USB transfer stall、電波断などについて、初期要件では厳密な復旧動作を規定しない。

ただし、例外によってアプリケーション全体がクラッシュしないようにする。

可能な限り状態をユーザーへ通知し、再接続・再選局・再初期化を行える構造とする。

# 44. 完成条件

初期バージョンの完成条件は、少なくとも以下を満たすこととする。

1. ChromeからRTL-SDR Blog V3/V4をWebUSBで認識・制御できる。
2. RTL-SDRから連続的にRaw IQデータを取得できる。
3. 日本国内のワンセグ放送を復調できる。
4. MPEG-TSを生成できる。
5. ワンセグの映像と音声をブラウザ上で再生できる。
6. 字幕を表示できる。
7. EPGを取得・保存・表示できる。
8. 番組表から選局できる。
9. チャンネルスキャンを実行できる。
10. EPGスキャンを実行できる。
11. 受信品質および処理状態を確認できる。
12. 処理遅延によるバッファ蓄積を確認できる。
13. ユーザー操作によってバッファを破棄してLIVE位置への復帰を試みられる。
14. Raw IQおよびMPEG-TSをデバッグ目的で保存できる。
15. 保存済みIQを使用して実機なしでDSPテストができる。
16. 保存済みTSを使用して受信機なしでTS解析・再生開発ができる。
17. GitHub Pagesから配信できる。
18. PWAとしてインストール可能である。
19. キャッシュ済み環境ではインターネット接続なしで起動し、RTL-SDRからワンセグ受信ができる。
20. 長時間受信時にもUIが著しく操作不能にならない。
