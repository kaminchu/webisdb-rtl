# Webブラウザ版ワンセグ受信アプリ 実装計画

対象: `plans/要件定義.md`（以下、要件定義書）

## 1. 本計画の位置づけ

要件定義書の「43. 開発方針」「44. 完成条件」を、実装可能な作業単位・成果物・検証方法・依存関係に落とし込む。

要件定義書が定める Phase 1〜8 を基本骨格としつつ、本計画では以下を追加する。

* Phase 0（プロジェクト基盤）を前段に追加
* 各 Phase の入出力・成果物・完了判定条件（DoD）を明確化
* レイヤー間インターフェースとディレクトリ構成を先行確定
* 実機なしで進められる開発・テスト経路（IQファイル / TSファイル）を各 Phase に組み込み
* 完成条件 20 項目との対応を最終章でトレース

方針は要件定義書に従い、**クライアントサイド完結・GitHub Pages 静的配信・PWA** とする。

## 3. 全体アーキテクチャ

### 3.1 データフロー（要件定義書 13 / 36）

```text
IQSource (RTLSDRSource | IQFileSource)
  ↓
Receiver Worker
  ├─ DC除去 → 周波数補正 → OFDM同期 → FFT
  ├─ キャリア復調 → TMCC解析
  ├─ デインターリーブ → Viterbi → Reed-Solomon
  └─ MPEG-TS生成
  ↓ (Transferable: Uint8Array)
TS Worker
  ├─ Demuxer
  │   ├─ Video  → Main Thread → WebCodecs VideoDecoder
  │   ├─ Audio  → Main Thread → WebCodecs AudioDecoder → AudioContext
  │   ├─ Caption→ Caption Processor
  │   ├─ PSI/SI → PAT/PMT/SDT/EIT/NIT/TDT/TOT
  │   └─ DataBroadcast（拡張ポイントのみ／初期未実装）
  └─ EPG / メタデータ → IndexedDB
Main Thread
  ├─ React UI
  ├─ IndexedDB
  ├─ Video / Audio 再生
  └─ Metrics / Buffer 可視化
```

### 3.2 Worker 境界

* **Receiver Worker**: WebUSB・RTL-SDR 制御・IQ 取得・IQ バッファ・DSP。
* **TS Worker**: MPEG-TS 解析・PSI/SI・EPG・メタデータ。
* 転送はまず `Transferable`（`ArrayBuffer`/`Uint8Array`）で実装。リングバッファや `SharedArrayBuffer` は Phase 7 の性能測定で必要性が出た場合のみ導入（COOP/COEP ヘッダ要件があるため GitHub Pages 制約に注意）。
* 各 Worker は同一のメッセージプロトコル型（`workers/protocol.ts`）で疎結合に接続し、Worker なし（同一スレッド）でもテストできるようコア処理は Worker 非依存モジュールに置く。

### 3.3 レイヤー疎結合の方針

* `IQSource` はデバイス非依存インターフェース（要件定義書 11）。
* `ISDBTReceiver` は `IQSource` のみに依存し、RTL-SDR 固有型を参照しない。
* `TransportStream` / `Demuxer` は `ISDBTReceiver` の出力バイト列にのみ依存。
* 各レイヤーは `interface` を介した依存性逆転とし、テスト時はフェイク実装に差し替える。

## 5. インターフェース先行定義

実装前に固定する境界。型定義を `src/models/` と各モジュールの `*.ts` に置く。

### 5.1 IQSource（要件定義書 11）

```ts
interface IQSource {
  open(): Promise<void>;
  close(): Promise<void>;
  setFrequency(hz: number): Promise<void>;
  setSampleRate(hz: number): Promise<void>;
  start(): Promise<void>;
  stop(): Promise<void>;
  onSamples(cb: (samples: Float32Array | Int8Array) => void): void;
}
```

### 5.2 DSP バックエンド差し替え境界（要件定義書 14）

```ts
interface FftBackend { forward(iq: Float32Array): Float32Array; }
interface ViterbiBackend { decode(input: Uint8Array): Uint8Array; }
interface RsBackend { decode(block: Uint8Array): Uint8Array; }
```

同一インターフェースの TypeScript 実装と（将来の）WASM 実装を `dsp/backend.ts` で選択。

### 5.3 主要データモデル（要件定義書 37）

```ts
interface PhysicalChannel { channel: number; frequency: number; }
interface Frequency { hz: number; }
interface TransportStream { tsId: number; services: Service[]; }
interface Service { serviceId: number; name: string; }
interface Event { eventId: number; serviceId: number; startTime: Date; duration: number; title: string; }
```

### Phase 1: RTL-SDR 接続（要件定義書 43 Phase 1, 4, 3）

**目的**: WebUSB で V3/V4 を認識・初期化し、連続 IQ を取得する。

**主な作業**
1. **WebUSB 基盤**: デバイス列挙、ユーザー選択、open、configuration 選択、interface claim、transfer 管理、reset、close。異常検出（transfer stall 等）。
2. **RTL2832U 初期化**: レジスタ初期化シーケンス、サンプルレート設定、USB 転送（Bulk IN）ループ。
3. **デバイス識別**: VID/PID + 文字列で Blog V3（R820T2）/ V4（R828D）を判定（`deviceProfile.ts`）。
4. **チューナー制御**: `Tuner` インターフェース + R820T/R828D 実装。周波数設定、gain 設定、AGC、PPM 補正。
5. **IQSource 抽象化**: `RTLSDRSource` と `IQSource` インターフェースを実装。IQ フォーマット（U8 I/Q）変換。
6. **確認 UI**: 簡易スペクトラム表示（FFT は仮実装で可）で IQ 取得を目視確認。
7. **メトリクス**: USB throughput / IQ input throughput / dropped samples の計測基盤。

**成果物**: `src/driver/rtlsdr/*`, `src/iq/RTLSDRSource.ts`, 接続・スペクトラム画面。

**DoD**
* Chrome（Win/macOS/Android）で V3/V4 を open→初期化→選局→連続 IQ 取得できる。
* スペクトラムに放送局らしきピークが観測できる。
* USB 抜去・stall でアプリがクラッシュしない（要件定義書 39）。
* transfer ループの単体テスト（モック USB）が通る。

**依存**: Phase 0。

**リスク**: Android Chrome の WebUSB 権限・OTG 挙動。実機検証必須のため、モック WebUSB 層を用意し実機依存を局所化。

---

### Phase 2: ISDB-T 同期（要件定義書 43 Phase 2, 13）

**目的**: IQ から OFDM 同期・FFT・TMCC 取得まで。実機なしで開発可能にする。

**主な作業**
1. **IQFileSource**: `.iq` + `.iq.json` メタ（sample rate / center freq / gain / ppm / timestamp / device / tuner）読み込み（要件定義書 34, 33）。テスト用 IQ 生成スクリプト。
2. **DC 除去**: 移動平均 / 高域通過。
3. **周波数補正**: キャリア周波数オフセット推定・補正。
4. **OFDM 同期**: ガードインターバル相関によるシンボル同期、整数/小数周波数オフセット。
5. **FFT**: radix-2/4 実装（`FftBackend` 経由）、窓・スケーリング。ISDB-T モード定数（Mode 1/2/3、キャリア数、GI 比）を `isdbtParams.ts` に定義。ワンセグは 1/13 セグメント（432 キャリア）。
6. **チャネル推定・等化**（同期の一部として）。
7. **TMCC 解析**: TMCC キャリア復調、差分復号、レイヤー構成・変調方式・符号化率・セグメント数取得。
8. **メトリクス**: Signal level / C/N / Frequency offset / MER 相当。

**成果物**: `src/dsp/stages/{dcRemoval,frequencyCorrection,ofdmSync,fft,tmcc}.ts`、`IQFileSource`、IQ フィクスチャ、同期確認 UI（コンステレーション/スペクトラム/TMCC 表示）。

**DoD**
* 保存済み IQ から OFDM シンボル同期が安定し、TMCC が継続取得できる。
* TMCC からモード・変調・符号化率がデコードできる。
* 周波数オフセットが計測・補正され、C/N 等が算出できる。
* IQ→TMCC の回帰テスト（同一 IQ → 同一 TMCC）が存在する。

**依存**: Phase 1（実機確認）、ただし IQFileSource により並行開発可能。

---

### Phase 3: ワンセグ復調（要件定義書 43 Phase 3, 13）

**目的**: キャリア復調から MPEG-TS 生成まで。

**主な作業**
1. **キャリア復調**: DQPSK（ワンセグ）復調、周波数・時間デインターリーブ。
2. **デインターリーブ**: 周波数インターリーブ / 時間インターリーブ解除。
3. **Viterbi**: 畳み込み符号（拘束長 7、パンクチャ）復号。`ViterbiBackend` 境界。
4. **Reed-Solomon**: RS(204,188) 復号＋誤り訂正、TS パケット再構成（同期バイト 0x47）。
5. **TS 生成**: 188byte パケット化、連続出力、TS 統計（packet error / BER）。
6. **性能測定**: TypeScript 実装のスループット計測、WASM 化候補の特定（要件定義書 14）。

**成果物**: `src/dsp/stages/{carrierDemod,deinterleave,viterbi,reedSolomon,tsGenerator}.ts`、`dsp/backend.ts`。

**DoD**
* 保存済み IQ から MPEG-TS が出力される（TS 同期バイトが連続、PAT PID=0x0000 が観測可能）。
* 同一 IQ に対する出力 TS（またはそのハッシュ）が毎回一致する回帰テスト。
* TS packet error / BER が計測できる。
* DSP 処理速度を計測し、リアルタイム比をレポートできる。

**依存**: Phase 2。TS 解析（Phase 4）とは `TransportStream` 境界で並行開発可能。

---

### Phase 4: TS 解析（要件定義書 43 Phase 4, 23, 24）

**目的**: MPEG-TS を独立モジュールとして解析。TS ファイル入力でも開発可能にする。

**主な作業**
1. **TransportStream / packet**: 188byte パケット、PID 多重分離、CC 管理、セクション再構成、CRC32。
2. **Describers 基盤**: 共通ディスクリプタパーサ。
3. **PSI/SI**:
   * PAT（PID=0x0000）
   * PMT
   * SDT（サービス名・事業者）
   * EIT（p/f、schedule、extended）
   * NIT（ネットワーク・TS 情報）
   * TDT/TOT（現在時刻、地域時差）
4. **TSFileSource / 入力切替**: 保存 TS を TS Worker へ直接入力（要件定義書 35）。受信系と解析・再生系を分離。
5. **TS Worker**: Demuxer を Worker 化、Demux 結果をチャネル別に配信。
6. **統計・Debug UI**: PID 一覧、TS 統計、PSI/SI 一覧、生データ表示（要件定義書 24）。

**成果物**: `src/ts/**`, `src/workers/ts.worker.ts`, TS 入力画面、Debug UI（PSI/SI）。

**DoD**
* 保存済み TS から PAT/PMT/SDT/EIT/NIT/TDT/TOT が正しく解析・表示される。
* RTL-SDR なしで TS 解析・UI 開発ができる（要件定義書 35）。
* 各セクションパーサの単体テスト（実データ抜粋＋合成データ）が存在する。
* Debug UI で PSI/SI、PID、統計を確認できる。

**依存**: なし（Phase 3 と並行可能）。Phase 5〜6 の前提。

---

### Phase 5: 映像・音声（要件定義書 43 Phase 5, 25, 26）

**目的**: Demux した PES から WebCodecs で再生。

**主な作業**
1. **PES → ES 復元**: 映像 H.264 / AVC、音声 AAC（ワンセグは HE-AAC）の PES 組立、タイムスタンプ（PTS/DTS）。
2. **VideoDecoder**: WebCodecs 設定（AVC config は PMT ディスクリプタから）。フレーム描画。
3. **AudioDecoder**: AudioContext 連携、再生バッファ管理。映像・音声同期（`avSync.ts`）。
4. **フォールバック検討**: WebCodecs 不可時の MSE/fMP4 経路は設計上の拡張ポイントとして整理（初期は WebCodecs 優先）。
5. **再生 UI**: 映像表示、音量、再生状態。

**成果物**: `src/media/{videoDecoder,audioDecoder,avSync}.ts`, Player 画面。

**DoD**
* 保存済み TS から映像・音声が再生される。
* 映像と音声の同期が維持される。
* 長時間再生でメモリ・バッファが破綻しない。
* Decoder 再同期（Phase 7 の LIVE 復帰）から復帰できる構造になっている。

**依存**: Phase 4。

---

### Phase 6: 字幕・EPG（要件定義書 43 Phase 6, 20, 21, 22, 27）

**目的**: 字幕表示、EPG 取得・保存・番組表 UI、EPG スキャン。

**主な作業**
1. **字幕**: PMT の字幕ストリーム（ARIB キャプション）を分離。ARIB STD-B24 8単位符号・外字変換（`data/arib/`）。字幕管理・表示（映像上オーバーレイ or 専用 UI）。映像/音声/字幕を独立ストリームとして扱う（要件定義書 27）。
2. **EPG モデル・取り込み**: EIT[p/f]/[schedule] を `Event` に正規化。TSID/サービス/イベントの関連付け。
3. **IndexedDB**: `stations` `services` `events` `epg` `scanResults` `receptionHistory` ストア、リポジトリ層、マイグレーション（バージョン管理）。有効期限・古い番組削除。
4. **番組表 UI**: 複数局横断表示、過去取得分の表示、番組選択で選局。
5. **EPG スキャン**: 受信可能チャンネルを順次選局し EIT を収集・保存（要件定義書 20）。

**成果物**: `src/media/caption/**`, `src/storage/**`, `src/features/epg/**`, EPG スキャナ。

**DoD**
* 字幕が映像または専用 UI に表示される。
* EPG が IndexedDB に保存され、未受信局も過去データから番組表表示できる。
* 番組表から選局できる。
* EPG スキャンが完走し結果が保存される。
* DB マイグレーションと有効期限処理のテストがある。

**依存**: Phase 4（PSI/SI）、Phase 5（表示）。

### Phase 7: UX（要件定義書 43 Phase 7, 16, 18, 19, 30, 31, 32）

**目的**: 選局・スキャン・受信品質・バッファ制御・Debug UI。

**主な作業**
1. **選局**: 物理チャンネル 13〜52、周波数直接指定、地域選択（`region` 機能）。周波数テーブル（関東圏の 6MHz 間隔等）を `channels.json` に。
2. **チャンネルデータ**: `regions/transmitters/channels/stations.json` + `version`/`updatedAt`。取り込みスクリプト。コードと独立更新可能な構造。
3. **GPS**: Geolocation API を **ユーザー操作時のみ** 要求（起動時要求禁止、拒否時も手動選択可）。現在地→地域自動選択。
4. **自動スキャン**: 物理チャンネル順次受信、検出（物理ch/周波数/受信可否/Signal level/C-N/MER/放送局名/Service ID/TSID）。
5. **受信品質表示**: Signal level/C/N/MER/BER/TS packet error/Frequency offset/USB・IQ・DSP throughput/Dropped samples/DSP 処理時間/Buffer occupancy。一般 UI と Debug UI で項目分離。
6. **バッファ可視化**: Buffered samples/bytes/occupancy/Estimated delay/Dropped samples/throughput。プログレスバー＋遅延秒表示。
7. **バッファ破棄 / LIVE 復帰**: IQ Buffer clear → DSP state reset → OFDM 再同期 → TS 再同期 → Decoder 再同期 → 最新位置から再開。
8. **Debug UI 総合**: PSI/SI、TMCC、PID、TS 統計、生データ、dump 操作（要件定義書 24, 33）。
9. **dump**: Raw IQ / MPEG-TS / TMCC / PSI-SI / DSP 統計 / Receiver ログ。IQ dump にメタ付与（`.iq` + `.iq.json`）。

**成果物**: `src/features/{region,scan,debug,receiver}/**`, `src/metrics/**`, `src/dump/**`。

**DoD**
* 3 方式の選局が動作する。GPS は明示操作時のみ要求し、拒否時も手動選択可能。
* スキャン結果が規定項目を取得・保存・表示する。
* 品質・バッファ指標が表示され、蓄積が可視化される。
* LIVE 復帰操作で遅延が解消され、復調・再生が再開する。
* dump ファイルとメタが保存できる。

**依存**: Phase 1〜6。

### Phase 8: PWA（要件定義書 43 Phase 8, 10, 9）

**目的**: オフライン起動・インストール可能・GitHub Pages 配信。

**主な作業**
1. Service Worker（プリキャッシュ: HTML/JS/CSS/WASM/アイコン/チャンネル・地域データ/静的アセット）。
2. `manifest.webmanifest`（名称・アイコン・起動モード）。

**成果物**: `public/sw.js`（または生成設定）, `manifest.webmanifest`, `deploy.yml`。

**依存**: Phase 1〜7。

## 7. 横断的設計方針

### 7.1 エラー処理（要件定義書 39）

* USB 抜去/OTG 切断/スリープ/バックグラウンド/stall/電波断でクラッシュさせない。
* 状態を `receiverController` に集約し、UI へ通知。再接続・再選局・再初期化操作を提供。
* Phase 1 から `try/catch` と状態機械を導入し、各 Phase で回復経路を追加。

### 7.2 サンプルレート（要件定義書 12）

固定せず技術設計事項とする。判断材料: RTL-SDR 安定動作 / USB 転送量 / Android 性能 / ワンセグ抽出方式 / DSP 計算量 / 周波数補正 / OFDM 同期精度。Phase 2 で候補（例: 1.2 / 2.0 / 2.4 MSps 等）を実測比較し決定。`config` で切替可能にする。デシメーション処理も `dsp/stages` に追加できる構造とする。

### 7.3 WASM 移行（要件定義書 14）

* Phase 3/7 で TypeScript 実装のスループットを計測。
* ボトルネック（FFT/OFDM/デインターリーブ/Viterbi/RS 等）のみ WASM 化。
* `dsp/backend.ts` のインターフェースで TS/WASM を差し替え、同一回帰テストで等価性検証。

### 7.4 拡張ポイント（要件定義書 28, 42）

* Demuxer に `DataBroadcast` チャネルを型として用意（表示処理は実装しない）。
* PSI/SI テーブルパーサは登録式にして追加可能に。
* チューナーは `Tuner` 実装追加で対応拡張。他 SDR は `IQSource` 実装追加で対応。

### 7.5 チャンネルデータ運用（要件定義書 17）

* JSON に `version` / `updatedAt` を持たせ、Service Worker キャッシュと IndexedDB の更新を分離。
* 取り込み・検証スクリプト（`scripts/fetch-channel-data.ts`）でコードから独立更新。

## 8. テスト戦略（要件定義書 34, 35, 40）

| 種別 | 対象 | 方法 |
| --- | --- | --- |
| 単体 | DSP 各段、TS パーサ、モデル、storage | Vitest |
| 回帰 | IQ→TMCC、IQ→TS、TS→PSI/SI、字幕変換 | フィクスチャ + スナップショット/ハッシュ比較 |
| 結合 | Demuxer→Decoder、Worker メッセージ | Worker をスレッド非依存モジュール化し直接呼び出し |
| ドライバ | RTL-SDR 制御 | WebUSB モック（`navigator.usb` スタブ）でのシーケンス検証 |
| 手動実機 | V3/V4、Chrome Win/macOS/Android | チェックリスト（接続・選局・スキャン・長時間） |
| 性能 | DSP スループット、バッファ | ベンチスクリプト + 実機計測 |

フィクスチャ方針:
* IQ: 短時間の録音（複数チャンネル・複数 SNR）。ライセンス確認の上で再配布可否を判断。
* TS: 実放送から取得した短尺 TS（権利に配慮しテストローカル限定を検討）。
* 合成: 既知の TS/PSI/SI を生成するテストビルダーも用意。

CI（`ci.yml`）: `oxlint` → `oxfmt --check` → `tsc --noEmit` → `vitest run` → `knip`。

## 10. リスクと対応

| リスク | 影響 | 対応 |
| --- | --- | --- |
| Android WebUSB/OTG の不安定さ | Phase 1 停滞 | モック層で分離、早期実機検証、transfer 再試行 |
| RTL-SDR Blog V4（R828D）初期化差 | V4 非対応 | `deviceProfile` で分岐、V3 先行→V4 追加 |
| ISDB-T 同期・復調の難度 | Phase 2/3 長期化 | IQ フィクスチャ集中開発、段階的に TMCC→TS を検証、参照仕様（ARIB STD-B31）精読 |
| DSP のリアルタイム未達 | 視聴不可 | 早期ベンチ、Worker 分割、WASM 化で対応 |
| WebCodecs の AAC/AVC 対応差 | 再生不可 | 対応確認の上、MSE/fMP4 フォールバック設計 |
| IndexedDB/キャッシュ肥大 | 容量圧迫 | TTL・世代管理・削除 UI |
| チャンネルデータの権利/正確性 | 表示不正確 | 出典明記、バージョン管理、ユーザー補正可 |
| SharedArrayBuffer の COOP/COEP 制約 | 転送方式制限 | まず Transferable、必要時のみ検討 |
